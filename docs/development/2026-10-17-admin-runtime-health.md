# 新版后台运行健康与发布核验基线

日期：2026-10-17

## 背景

PR #519 已完成新版后台工作区细分、字段定位搜索与中文补查，并通过受控生产发布。后续进入稳定运营阶段，Issue #258 要求继续核对生产版本一致性、服务健康、5xx/异常与回滚能力。

本阶段先补应用进程能够可靠证明的只读健康真值，不把应用自身无法证明的 nginx、systemd 或主机 release 状态伪装成后台状态。

## 本阶段能力

新增 `GET /api/admin/xingwei/runtime-health`，要求 `deploy:view`：

- 当前 JVM 启动时间与运行时长；
- JVM 已用/最大堆内存与线程数；
- 数据库 `SELECT 1` 连通状态与检查耗时；
- 当前 JVM 启动后的请求总数、4xx、5xx；
- 最近一次 5xx 的时间与状态码。

响应使用 `Cache-Control: no-store`。

## 隐私与安全边界

请求基线只记录聚合状态码，不记录 URL、查询参数、请求体、账号、IP、业务编号或其他业务数据。数据库异常只转换为 `up=false`，不返回 JDBC URL、数据库账号、异常消息或 SQL 细节。

静态 `/assets/**` 与 favicon 不计入业务请求基线，减少资源噪声。

该接口是只读诊断，不执行重启、发布、回滚、支付、退款、企业微信目录写入或其他外部操作。

## 不由应用进程声明的状态

以下项目继续由 GitHub 发布流水线和生产主机核验，而不是由应用 API 自证：

- `current-release.env` 对应 Git SHA / JAR SHA256；
- nginx 当前 upstream 是否为 8080；
- `xinghuo-v2.service` 的 systemd 状态；
- 上一版本 release / symlink 回滚路径；
- systemd/nginx 历史日志和主机级异常。

这样可以避免“应用自己报告自己已正确部署”的循环证明。

## 验收

- `deploy:view` 以外的星维角色不能读取运行诊断；
- 数据库正常时 `database.up=true`，连接异常时返回 `false` 且接口本身仍可响应；
- 4xx 与 5xx 分开累计，最近 5xx 仅保留时间和状态码；
- 不保存或返回请求路径和业务内容；
- 无数据库 migration、无生产配置变更；
- Maven、权限契约与 Chromium/WebKit 全量 CI 继续作为合并门禁。

## 下一步

在该服务内真值稳定后，再把 Issue #258 的主机级发布核验和真实生产后台关键路径验收记录收口；如需在后台增加可视化“运行健康”页面，应直接消费该只读接口，不建立第二套状态来源。
