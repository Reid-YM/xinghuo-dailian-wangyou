# 微信支付退款后的成功通知重放保护

## 问题与处理

Native 支付回调与主动查单共用 `applySuccess`。原逻辑仅对 CAPTURED 状态做幂等判断；REFUNDED 状态再次收到原交易 SUCCESS 时，会尝试回写 CAPTURED 并插入收款流水。已有流水时可能触发唯一约束、导致整个通知事务回滚并反复重试；缺少原流水时则可能把退款状态覆盖为已支付，影响后台到账展示与履约门禁。

本次将 REFUNDED 纳入已处理收款状态。在锁定支付单后，仍先验证商户、应用、金额和币种，再核对原微信交易号；一致则保留退款状态、原到账时间及已有流水，不新增收款。不同或缺失的原交易号继续报错并交由人工核查，不静默接受。

通知事件编号去重继续保留。不同事件编号但同一交易的退款后 SUCCESS 可以正常处理为 SUCCESS，避免重复重试。CANCELLED 后收到经核实的真实成功交易仍记录到账，防止遗漏实际收款。本次不增加退款接口，不改变退款业务流程。

## 回归范围

- 原交易入账后标记退款，再以新事件编号重放成功通知；退款状态与单条收款流水均保留，新事件可幂等处理。
- 对已退款支付单重复主动查单；不创建收款流水、不恢复 CAPTURED，即使历史收款流水缺失也不自动重建。
- 已退款记录原交易号不同或为空时拒绝自动处理。
- 退款后重放通知仍必须通过金额校验。
- 已关闭支付单收到真实成功查单结果仍仅入账一次。

测试使用隔离 H2 数据库与模拟微信 SDK，不请求真实商户、不写入生产业务数据。

本地 Java 21 验证：支付服务定向测试 11 项全部通过；`mvn -B -ntp clean package` 共 836 项，失败和错误均为零，173 项浏览器环境条件跳过。版本状态校验、409 项搜索索引校验与 `git diff --check` 通过。标准 Chromium/WebKit 由 PR CI 另行执行。

## 交付边界

仅修改 Native 服务共用到账处理及其测试；账号和游客支付均沿用此到账处理。无数据库迁移、生产配置、凭据、权限或认证变更。回滚可通过恢复本次代码实现，但会重新暴露上述重放问题。生产发布和真实商户回调验收独立于代码与 CI 验证。
