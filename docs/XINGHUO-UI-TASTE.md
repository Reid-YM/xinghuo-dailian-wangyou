# 星火网站 UI Taste 设计与实现规范

> 适用范围：星火网站前台、后台、用户中心、攻略页、工具站、登录/注册、表单、列表、详情、配置页、Dashboard 与响应式界面。
>
> 本规范用于补充根目录 `AGENTS.md`。涉及 UI、布局、视觉、交互、响应式、前台可配置能力的任务，应在修改代码前阅读本文件。

## 1. 目标

星火 UI 不追求“看起来像一个流行模板”，而要做到：

- 用户一眼知道当前页面是做什么的、下一步做什么；
- 前台强调可信、清晰、转化和服务进度；
- 后台强调扫描效率、配置效率、状态清晰和误操作防护；
- 视觉语言来自真实业务、游戏服务、订单/询价/进度/攻略/工具等内容，而不是来自通用 SaaS 模板；
- PC、24 寸宽屏、常规笔记本与手机端都像经过专门设计，而不是简单拉伸或压缩；
- 保持现有业务能力与数据契约，UI 优化不得擅自改变核心业务逻辑。

## 2. UI 任务开始前：先建立 Visual Thesis

在写 HTML/CSS/JS 前，先用下面字段快速确定设计论点。内部思考即可；重大改版或 PR 说明中应保留关键结论。

```text
product_type: 当前页面属于运营工具 / 用户中心 / 电商服务 / 内容 / 工具站 / 品牌页面中的哪类
subject: 这个页面具体服务什么业务对象
user_pressure: 用户此时最在意速度、信任、比较、确认、学习还是风险控制
single_job: 此页面最重要的一件事
primary_workflow: 用户最常重复的操作路径
density: compact / balanced / spacious / editorial
tone: 两个准确形容词，禁止只写“现代、简洁”
palette_roles: 现有品牌色与功能色分别承担什么角色
type_roles: 标题、正文、标签、数据分别如何建立层级
layout_concept: 一句话说明布局为什么这样组织
signature_device: 一个来自星火业务本身的识别性视觉规则
aesthetic_risk: 一个有观点但不伤害可用性的设计选择
anti_template_rejection: 本次明确拒绝的模板化做法
```

如果换掉“星火”名称后，同一套布局、文案、卡片和装饰可以原封不动用于任意 SaaS，那么设计仍然过于模板化。

## 3. 两轮审美与实现循环

### 第一轮：先定结构

1. 找出页面唯一主任务。
2. 按信息优先级分配首屏空间，先预算视口，再放组件。
3. 用真实业务内容和真实状态设计，不用 lorem ipsum 或空壳卡片决定布局。
4. 明确哪些内容必须首屏可见，哪些可折叠、分组或进入二级页。
5. 决定一个业务相关的视觉签名，不靠额外装饰制造“设计感”。

### 第二轮：反模板检查

逐项询问：

- 颜色、字体、卡片、图标、间距是否只是 AI 常见默认选择？
- 是否为了“高级”增加了没有信息价值的玻璃、渐变、光斑、悬浮卡片？
- 是否把本应连续阅读或连续操作的内容拆成过多卡片？
- 是否因为追求视觉表现牺牲了数据密度、表单效率或移动端操作？
- 实现后的页面是否又退回普通模板，而偏离最初 Visual Thesis？

先修正结构与层级，再做装饰性细节。

## 4. 星火前台模式

前台包括首页、服务/商品、询价、用户中心、攻略、工具站以及面向客户的状态页面。

### 4.1 首屏必须回答

根据页面类型，首屏应尽快回答用户真正关心的问题，例如：

- 这里提供什么服务或工具；
- 当前可做什么；
- 价格/询价/进度/结果从哪里进入；
- 为什么值得信任；
- 下一步按钮在哪里。

不要为了视觉冲击使用与任务无关的超大 Hero，把真正功能推到首屏以下。

### 4.2 内容必须业务化

优先使用：

- 游戏、服务、奖励、段位、进度、订单、询价、攻略、工具结果等真实业务对象；
- 明确的服务状态、流程状态和用户下一步；
- 能证明可靠性和可追踪性的内容。

禁止把数据库字段名、内部配置键、开发术语、后台实现细节直接暴露给普通用户。

### 4.3 转化不等于堆按钮

一个区域只保留明确主行动；次行动降低视觉权重。按钮文案应描述动作结果，不使用模糊的“点击这里”“更多”等作为关键 CTA。

## 5. 星火后台模式

后台是运营工具，不是展示站。默认方向：安静、紧凑、可扫描、可预测。

### 5.1 信息架构

- 导航名称使用业务语言，不使用代码名或数据库表名。
- 列表页优先支持扫描、筛选、定位和批量判断。
- 编辑页按任务分组，不为了视觉统一把所有字段塞进同一种卡片。
- 同一业务对象的列表 → 详情 → 编辑路径保持一致。
- 主要按钮位置、返回路径、保存反馈在不同后台页面保持稳定。

### 5.2 表单与配置页

每个可配置项必须尽可能提供：

- 人能理解的中文标签；
- 必要时提供简短帮助文字或示例；
- 合理默认值；
- 格式、范围和必填校验；
- 成功/失败反馈；
- 对高风险操作的明确确认。

如果某项配置会影响前台视觉，优先提供可理解的预览或结果说明。不要要求运营人员理解 CSS、JSON、数据库键名或内部枚举才能完成日常配置。

### 5.3 前端可配置能力

当需求明确要求“后台可配置前台”时：

- 常规文案、图片、开关、排序、展示参数等应从后台可维护；
- 配置名称应与前台实际效果一一对应；
- 不允许出现“后台有字段但前台无效果”或“前台展示但后台找不到配置入口”的断链；
- 对会破坏布局的自由输入设置边界、尺寸或格式校验；
- 默认值必须保证前台在未配置时仍可正常展示；
- 新增配置不能擅自破坏已有兼容行为。

## 6. Dashboard、表格、列表与卡片

### Dashboard

- 指标服务于判断和动作，不为凑满页面而增加数字卡片；
- 重要异常、待处理项和下一步动作优先于装饰性统计；
- 同类数据统一对齐和格式；
- 趋势、状态和比较必须有语义，不只靠颜色。

### 表格 / 列表

- 优先保证列的可读性、对齐、排序和操作效率；
- 数值、日期、状态、操作列使用稳定格式；
- 关键动作不要藏在难以发现的 hover-only 交互里；
- 空数据、无搜索结果、加载失败必须有明确状态；
- 手机端不要机械压缩桌面大表格：按任务选择优先列、卡片化详情或有意识的横向滚动。

### 卡片

卡片只用于表达真实分组、状态或独立对象。禁止“卡片套卡片”和为了留白把每一段内容都做成悬浮卡片。

## 7. 反模板清单

没有业务理由时，默认拒绝：

- AI 产品常见的紫蓝霓虹渐变；
- 大量玻璃拟态、背景模糊、bokeh 光斑；
- 与工作流无关的通用 Bento Grid；
- 漂浮页面区块和卡片套卡片；
- 后台、编辑器、Dashboard 使用占据大量首屏的巨大 Hero；
- 仅由同一颜色不同明度组成的单色调界面；
- 装饰性圆球、Blob、无语义抽象 SVG；
- 用大量微型 badge 和微文案代替真正的信息层级；
- 每个元素都有动画；
- 只因当前流行就加入、但与星火业务无关的视觉组合。

这些不是绝对禁令。若品牌、业务内容或明确需求确实需要，必须能解释它为什么属于当前页面。

## 8. 视觉变量与现有设计系统

- 优先复用现有 CSS 变量、布局规则、组件和资源；
- 修改前先找出现有样式来源，不新增第二套互相冲突的设计系统；
- 品牌色、功能色、成功/警告/危险色应职责明确；
- 颜色不是唯一状态载体，状态还要有文字、图标或结构提示；
- 字号、字重、间距、圆角、边框应形成少量稳定层级，而不是每个模块单独发明；
- 如确需建立新 token，应统一命名并逐步收敛重复硬编码，而不是进行与当前任务无关的大重构。

## 9. 响应式要求

移动端不是桌面版缩小。

每次涉及布局的改动至少检查：

- 手机窄屏；
- 常规笔记本宽度；
- 24 寸/较宽桌面窗口；
- 极端长文案、长用户名、长服务名；
- 图片缺失或比例异常；
- 浏览器缩放后关键操作是否仍可使用。

原则：

- 宽屏不能只靠固定最大宽度制造大面积无意义黑边/空白；
- 文本不得被图片遮挡；
- 核心按钮不得因为换行、固定高度或绝对定位而不可操作；
- 表单控件与触控目标在手机端保持可点击；
- 断点依据真实布局需求，不为了“常见数字”机械新增。

## 10. 必须设计的状态

不能只设计“正常且有数据”的截图。与页面相关时必须覆盖：

- loading；
- empty；
- no results；
- success；
- error；
- disabled；
- form validation；
- permission denied；
- destructive confirmation；
- 超长内容；
- 图片/资源加载失败；
- 保存中与重复提交防护。

## 11. 动效

默认使用克制动效。动效只用于：

- 表达状态变化；
- 建立操作因果；
- 帮助理解展开/收起或页面层级；
- 为少量关键品牌体验增加识别度。

不允许“所有元素都动”。如果去掉某个动画后任务理解没有任何损失，通常可以不做。

## 12. 可用性与可访问性最低要求

- 主要操作无需额外教程即可发现；
- 表单有清晰 label、错误信息和提交反馈；
- 键盘焦点不应被全局 CSS 隐藏；
- 文字和背景保持足够对比；
- 图标按钮有可理解文本、title 或 aria-label；
- 关键状态不能只靠红/绿颜色区分；
- 弹窗、抽屉、下拉等打开后不能造成明显的焦点/滚动陷阱。

## 13. UI 改动的验证顺序

完成实现后按顺序检查：

1. **业务正确**：原功能、路由、提交、保存和权限没有被 UI 改坏。
2. **主任务清晰**：目标用户不读解释也知道下一步。
3. **层级正确**：层级主要由布局、排版、间距建立，而不是装饰。
4. **业务特异性**：页面看起来属于星火，而不是任意创业公司模板。
5. **真实状态完整**：空、错、加载、长内容等边界可用。
6. **PC / 手机**：至少检查桌面与手机；涉及宽屏问题时增加 24 寸/宽窗口检查。
7. **配置闭环**：后台配置与前台结果确实对应。
8. **实现无漂移**：最终代码仍符合最初 Visual Thesis，没有回落到默认模板。

## 14. PR 交付说明

明显 UI 改版的 PR 说明至少写清：

```text
Visual thesis:
Signature device:
Aesthetic risk:
Rejected generic choice:
Density / motion:
Intentional tradeoff:
Responsive checks:
States checked:
Functional validation:
```

若环境允许，应附关键页面桌面端与手机端截图。若未能实际渲染或未能完成某项验证，必须明确说明，而不是写成“已验证”。

## 15. 最终 Good-Taste Gate

交付前最后确认：

- 用户能否快速完成最重要的任务？
- 主操作是否明显但不过度喧闹？
- 页面层级是否来自结构而不是装饰？
- 是否能看出这是星火的产品，而不是通用模板？
- 是否有足够真实状态来判断界面质量？
- 手机端是否像重新设计过，而不是被压缩？
- 是否只有 1–2 个主要表现轴，而不是处处抢注意力？
- 是否存在一个可记住、且真正帮助业务理解的视觉规则？
- 每个结构、卡片、颜色、动画是否都能说明自己的信息意义？

通过以上检查后，再进行细节抛光。
