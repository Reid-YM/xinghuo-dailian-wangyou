# V4F 客户补充待跟进

V4E 客户补充已经出现在员工队列和详情；V4F 增加“客户补充：待跟进”筛选。后台按原有 `order:view` 与 ALL / DEPARTMENT / SELF 范围先过滤、计数，再分页；已解决的记录收到补充后仍可出现在待跟进筛选中，但状态不会自动变更。

客服打开详情时，浏览器记录当时看到的最新补充 ID。只有持有 `order:manage` 的员工完成原有带 `expectedVersion` 的处理动作时，才把已查看的补充游标向前推进；旧客户端不提交游标则不确认。服务端验证游标属于该售后记录，拒绝跨记录或伪造编号。若客户在员工阅读之后补充，新内容的 ID 高于所提交游标，仍保留待跟进。处理说明、客户公开回复和 V72 事件继续按既有规则写入，状态是否变化由客服明确选择。

V74 仅在 V71 状态表增加默认 0 的游标列，旧版本插入/更新可继续运行，适合 18080、8081、8080 并行切换。精确 Git blob hash 已纳入迁移审核清单。回滚 JAR 不会回退 V74 列或已确认游标；数据库数据保留。无需生产配置，也不触发退款、真实收款或企业微信写入。V3H 小程序支付 PR #384、企业微信写入 PR #372 继续独立验收。

发布路径：功能 PR 与主线 Java/Maven、Chromium/WebKit CI → `deploy/production` 的 `.deploy-request` 精确主线 SHA → 18080、8081、8080 与发布后核验。生产通过后，再将后台阶段和 Release History 从候选同步为已上线。
